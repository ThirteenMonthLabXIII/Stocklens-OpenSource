# 阶段 6：Qt 工作台改造

本阶段把 Qt 条件选股页收口为“确定性候选 + 证据状态”工作台。Agent 只整理当前不可变快照中的证据，不能新增、删除、排序、评分、升级候选或执行加入观察动作。

## 已实现

- 条件选股页默认使用 `formal`，并提供 `review_only`、`exploratory` 两个明确模式。
- `review_only` 和 `exploratory` 结果在页面和结果明细中持续标识；两者不进入正式观察绩效样本。
- 候选列表展示 Candidate Lens、确定性资格、G 层当前状态、数据时间/来源、Agent status、覆盖度、支持证据、反向证据、冲突、数据缺口和后续核查条件。
- 筛选完成后，Qt 后台以完整候选集构造不可变证据包，自动运行五个 Agent；单包沿用阶段4的 30 只上限，超过 30 只时分批处理并合并展示，不再要求逐只进入研究页。单个 Agent 失败只影响对应证据状态，不改变规则候选集合。
- 证据包先持久化再检查 API Key；未配置 Key 时记录 `skipped/missing_api_key`，候选仍保留并提示“待配置后可重试”。重试入口只重试失败、跳过或未完成批次，不重新筛选或重复创建候选。
- F 层仅展示通过本地事实引用校验的 claim；Agent 未配置、失败或无有效引用时不填充支持证据，但失败、缺失和冲突信息仍保留。
- `SqliteEvidenceRunStore` 持久化每一批证据包、五 Agent 执行信封和 F 层摘要；同一快照与候选集再次筛选时优先跨重启逐批回放，加载时重新校验证据包哈希、Agent 编排哈希和 F 层摘要哈希。
- G 层通过 `CandidateStateService` 写入候选状态和迁移审计；“人工加入观察”要求 `human:<id>` actor，Agent 和自动规则没有该权限。
- exploratory Agent 的新候选只进入“探索待审”队列；人工正式复核必须使用原始快照、有效事实引用并重新通过 CandidateLens，正式化后仍需单独人工动作才能进入 `watch`。
- 从正式候选进入个股研究页时，旧交易观察/持仓按钮和旧 AI 入口隐藏并被动作守卫拦截；兼容后端字段仍可被旧流程读取，但不会从正式候选 UI 或导出 JSON/CSV 暴露。
- 导出的 Qt 候选结果不再包含 AI 分数、AI 排名、置信度或交易价格字段；旧存储字段继续保留为兼容读取边界。

## 本阶段边界

阶段6 的离线契约覆盖五 Agent 自动运行、30 只分批、证据包先持久化、缺 Key 可重试、跨重启回放和探索待审。若没有 API Key，系统不发起模型请求，候选仍显示确定性结果并明确标记 Agent 待重试；已有持久化结果优先本地回放。
