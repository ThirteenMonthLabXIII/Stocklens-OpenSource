# 阶段 5：证据汇总与候选状态

阶段 5 已完成。它在阶段 4 五 Agent 编排之后增加两个本地层：

```text
AgentResult v1（已校验）
→ F 层结构化证据汇总
→ G 层本地候选状态
→ 人工明确加入观察
```

实现入口：

- `stock_tool/core/evidence_summary.py`
- `stock_tool/core/candidate_state.py`
- `tools/test_phase5_evidence_summary.py`

## F 层合同

`aggregate_agent_evidence()` 只接受当前证据包和阶段 4 已生成的执行记录/`AgentResult`。它会再次确认：

- 证据包哈希、快照和事实引用仍然有效；
- Agent 结果的 `snapshot_id`，以及执行信封中的 `candidate_set_digest`、`evidence_package_hash` 与证据包一致；
- 执行信封与 AgentResult 的 `status`、`run_id` 一致；
- claim 只绑定已有 `claim_id`，重复或失效引用不进入汇总；
- failover 事实不进入 verified claim；
- 编排结果的候选集合与证据包完全一致。

每个候选的 F 输出包含：

```text
status: ok | partial | failed
supporting_claim_ids
opposing_claim_ids
conflicts
unresolved_questions
data_quality_summary
candidate_type_labels
```

冲突使用支持/反向 claim ID 原样保留，不平均、不生成分数、不生成排名。`candidate_type_labels` 只取确定性候选记录已有的 `lens_ids`。

F 层禁止输出 `candidate_status`、`rank`、`score`、`confidence`、买卖字段和目标价等决策字段。五 Agent 全部失败时，F 状态为 `failed`，但候选记录仍保留。

## G 层合同

`CandidateStateService` 只由本地规则计算状态，并持久化当前状态和追加式迁移记录。F 层要求一组完整且身份一致的五 Agent 执行记录；缺失执行记录、未知 Agent、快照/候选集/run_id 不一致都会拒绝汇总。支持的迁移主线为：

```text
eligible → candidate → watch → stale / invalidated / closed
```

数据缺口、冲突和过期分别进入 `insufficient`、`conflicted`、`stale`；这些状态不能自动升级为 `candidate` 或 `watch`。`invalidated` 和 `closed` 不自动复活。

加入 `watch` 必须调用显式人工动作，actor 必须使用 `human:<id>` 或 `user:<id>` 格式并提供 reason codes；Agent、F 层、G 层及本地规则均会被拒绝。每次迁移至少保存：

```text
candidate_id
from_status
to_status
reason_codes
actor
snapshot_id
created_at
```

状态当前值和迁移记录都提供内存实现和 SQLite 实现，便于 Qt 会话和持久化回放。阶段 5 不改 Qt 页面，不删除旧公式/旧交易 AI；正式页面接入属于阶段 6。
