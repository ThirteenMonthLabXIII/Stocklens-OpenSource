# Stocklens V3 正式发布说明（内部开发）

产品展示使用“Stocklens V3 / A股选股仪 V3”；程序和 manifest 的比较版本是 `3.0.0`，Windows 文件版本为 `3.0.0.0`。唯一版本源为 `stock_tool/config/release_identity.py`，任何窗口标题、Inno Setup 定义、安装器名称、版本说明路径、正式构建、manifest 和交付脚本都不得另写版本常量。

客户文档只说明商业包不含源码、数据库、缓存和密钥；不介绍编译器，也不作“不可反编译”承诺。内部构建固定 `Nuitka==4.1.3`、Nuitka 管理的 MinGW64、Windows standalone，不使用 onefile。Nuitka 的编译报告、资源清单和工具版本只进入内部 manifest 与 release-local 证据。

`requirements-v3.lock` 固定直接依赖、活动传递依赖及 standalone 科学计算依赖，并为每个发行物记录 SHA256；正式安装必须使用 `--require-hashes`。构建前会按已安装 distribution metadata 验证完整依赖闭包，缺包、版本漂移、哈希不符或传递依赖漏锁都会阻断候选构建。

构建机若 Python 安装路径含非 ASCII 字符，Nuitka 4.1.3 的旧 Dependency Walker 可能错误解析 DLL 路径；正式命令固定 `--experimental=force-dependencies-pefile`，仍由 Nuitka 管理 MinGW64，仅替换 DLL 依赖扫描器。

## 正式入口

```powershell
python -m pip install -r requirements.txt
python -m pip install -r requirements-build.txt
python -m pip install --require-hashes -r requirements-v3.lock
python tools\release_tooling.py --install
python tools\release_security_scan.py --source-tree
python tools\verify_release_signing.py --self-test
python tools\build_v3_nuitka.py --candidate-stage rc0
python tools\prepare_v3_release.py --candidate-stage rc0
```

构建仅接受干净 Git commit。输出固定为：

```text
dist/Stocklens_V3/Stocklens.exe
installer_output/Stocklens_V3_Setup.exe
release/V3_商业交付_<时间戳>/
```

`build.spec`、`build_qt.spec` 与 PyArmor/PyInstaller 链只用于一个兼容周期的历史包验证，正式批处理、安装包、V3 交付和 V3 验收均不调用它们。

## 双候选流程

1. RC0：从干净 commit 全新构建，运行完整自动化、Nuitka 包级 smoke、敏感扫描并在其他设备完成 P7 首轮人工矩阵。合同保持“部分对齐”。候选、构建和 release manifest 均为 schema 5，P7 为 schema 3。
2. 合同转正：只在 RC0 自动化与 P7 schema 3 人工证据齐全后，运行 `tools/promote_v3_rc0.py`。该步骤生成 schema 2、不含截图和个人路径的转正记录，更新 21 项合同状态、测试 ID 和记录引用，然后冻结 commit。
3. RC1：从包含转正记录的干净 commit 全新构建并运行：

   ```powershell
   python tools\build_v3_nuitka.py --candidate-stage rc1
   python tools\prepare_v3_release.py --candidate-stage rc1
   python tools\final_release_gate.py --release-dir <RC1目录>
   ```

RC1 的构建会强制 `tools/test_frontend_default_gate.py`，并在 build manifest 记录完整 Python/编译器/安装器身份、前端合同 SHA256、RC0 转正记录 SHA256 与 `requirements-v3.lock` 摘要。最终闸门会拒绝 RC0、未通过的默认合同、V3 release manifest schema 3/4、缺失的 Nuitka 证据、未通过的包级 smoke、必需人工项 `NA`/`FAIL`、候选哈希不匹配、截图伪装、RC0 截图复用、近重复截图未复核和 `--mark-all-pass`。Windows 10 可选兼容项的 FAIL 仅保留 warning。闸门还会验证当前 HEAD、干净工作树、合同与转正记录都属于 RC1 构建 commit。

候选准备阶段先用 Cosign 对 manifest、安装包、商业 ZIP 和源码 ZIP 逐件签名并回读验签，索引为 `release_local/signatures/CANDIDATE_SIGNATURES.json`。最终闸门先拒绝缺签、签名或 bundle 被改动的候选；其余检查通过后才原子生成并签名 `FINAL_RELEASE_DECISION.json`，形成五类 subject 的 `SIGNATURES.json`。Cosign、Gitleaks、Syft 的版本、官方 URL 与 SHA256 固定在 `stock_tool/config/release_tool_lock.json`；工具只安装到 `.toolcache/`，不写 PATH。加密私钥与密码只存 Windows 凭据管理器，仓库只提交公钥及 key id，运行时临时私钥必须清理。V3.0.6 本地密钥签名不依赖可选 TSA；验签优先使用本机缓存的 Sigstore trusted root，并对临时网络错误做有限重试，仍保留 bundle 与透明日志验签。

## 人工验收

RC 目录会生成带安装包、商业 zip、源码 zip SHA256 的 `V3_P7_人工验收清单.txt/json`。外部验收设备只需安装安装包、逐项操作并返回脱敏截图与 PASS/FAIL。

收到证据后，构造包含候选字段、项目状态和截图路径的 JSON，再执行：

```powershell
python tools\record_v3_p7_manual_acceptance.py --release-dir <RC1目录> --evidence-json <证据.json> --operator <验收人>
```

证据 JSON 还必须声明 `devices`（`device_id`、`windows_version`、`os_label`）以及每项的 `PASS`/`FAIL`/`NA`、观察备注和截图列表。该命令会复制截图到 `release_local/`，使用 Pillow 对 PNG/JPEG/WebP 执行完整解码并校验尺寸，计算文件 SHA256、标准化像素 SHA256 和 dHash，再将固定路径报告绑定到 RC commit、候选 manifest 与三种候选哈希；它不会改写候选 manifest。正式模式没有 `--mark-all-pass`；工具能防替换、错挂和未复核的近重复证据，证据真实性仍由实际操作者负责。

## 支持口径

- 正式支持 Windows 11 24H2 / 25H2 x64。
- Windows 10 22H2 x64 只做兼容性验证，不属于正式支持范围。PASS/FAIL 必须绑定 `win10_22h2` 设备；没有设备时填 NA。FAIL 会写入兼容性 warning 并撤销兼容声明，但不阻断 Windows 11 V3 转正和发布；客户文档不得声明 Windows 10 已正式支持或已验证通过。
- Qt 是默认且唯一普通用户界面；历史前端调用会被拒绝，Qt 故障显示脱敏错误并退出，不提供界面回退。
- 当前未配置 Windows Authenticode 发布者证书；Cosign 完整性签名不能替代 Authenticode，安装时可能显示“未知发布者”。
